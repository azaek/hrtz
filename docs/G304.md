# Logitech G304 / G305

Experimental support, based on a read-only G304 probe on 2026-11-18. This is not
yet a replacement for every G HUB feature. No hardware settings were written in
that session; do not mark the model tested until settings have been exercised
and restored on hardware.

## Observed hardware

| Item | Observed value |
|---|---|
| Receiver | USB 046D:C53F |
| Mouse identity | Wireless 4074; no USB/cable identity |
| HID++ transport | Vendor page FF00, short usage 1 and long usage 2 |
| Sensor DPI | 200–12,000, step 50 (2201) |
| Polling rates | 125, 250, 500, 1,000 Hz (8060) |
| Battery | Battery status 1000; not a rechargeable voltage estimate |
| Onboard memory | Format 3, one profile, six buttons, 255-byte sectors |
| Mode during capture | Host mode, controlled by G HUB |

The driver uses the wireless identity for the model name and model-specific
capabilities, without pretending 4074 is a wired USB product ID. The sixth
physical control is labelled DPI button even when assigned another action.

## Preserving existing functionality

The supplied mouse photo is displayed with a transparent background and a
selectable marker for the DPI button on top.

Connection and discovery do not change mode or settings. The existing driver
edits profile fields in a fresh copy of the sector and recalculates its checksum.
Unedited button records, alternate bindings, power-mode bytes and timeout bytes
remain intact. Macro memory is not touched by an ordinary profile edit.

Existing settings are preserved, but preservation does not imply that hrtz can
create or edit every vendor feature. Keep G HUB for macro editing, G-Shift
configuration, endurance/performance switching and software game profiles.
G HUB host mode remains in control; hrtz does not switch it off automatically.
Onboard changes may only become active after G HUB releases control.

Full backup, restore and factory reset are deliberately unavailable. The device
reports six sectors, but reads of 3, 4 and 5 return invalid argument. Sector 2
contains non-profile data without a profile checksum. Treating those reads as
erased sectors would create an incomplete backup. The existing full-memory test
report therefore cannot complete on this model either.

## Validation and remaining work

- Read-only discovery and profile checksum/decoding checked on a connected G304.
- Four standalone Rust checks passed against the captured profile: checksum and
  decoding, sensor range, byte preservation for polling edits, and byte
  preservation for DPI edits. These checks transform local bytes only.
- Driver regression tests cover wireless identity, capabilities, AA battery
  reporting, host-mode coexistence, preservation during polling edits, and
  rejection of unsupported memory operations.
- `cargo fmt --check` and `git diff --check` passed.
- `cargo test --lib hidpp`: 70 passed, with the opt-in hardware probe ignored.
- Frontend type-checking and the Vite production build passed.
- The optimized standalone Windows executable was built successfully with
  `cargo build --locked --offline --release --features tauri/custom-protocol`.
  It is at `src-tauri/target/release/hrtz.exe`. It has not been launched or used
  to change hardware settings during this build check.
- The Cargo TLS error was worked around with a local download relay using
  Python's verified upstream HTTPS. Dependencies remain pinned by the lockfile;
  subsequent Rust builds run offline. No hardware write test has been performed.

Before calling support complete: implement a
faithful backup format for the G304's accessible profile and macro memory;
verify each offered setting on hardware with restoration; verify endurance mode
behavior and its relationship to the report-rate control; and implement/test
the missing G HUB features needed for a complete replacement.
